Read `docs/briefs/COMMON.md` first. **You own:** `src/input/`, `src/ui/`, `src/audio/`, `.github/`, `README.md`, `dev/ui/`, `tools/ui/`, `e2e/controller*.spec.ts`, `e2e/ui*.spec.ts`. Browser APIs allowed (input/audio), but keep logic in pure, unit-testable modules.

## Mission
Make the game *playable, legible, audible and shippable*: a first-class **Nintendo Switch Pro Controller** experience over Bluetooth (plus Joy-Cons, Xbox/PlayStation pads, two keyboard layouts), a crisp **in-pixel UI/HUD** with Korean-minimalist restraint,
a fully **procedural WebAudio** engine with per-titan sonic signatures and an adaptive score, and the CI/CD + README that put it on GitHub Pages.

## 1. Input (`src/input`)
Export `createInputManager(opts?): InputManager` from `src/input/index.ts` (you design the interface; document it in `src/input/README.md`; the Lead integrates it). It must provide at least:
`attach()/detach()`, per-frame `poll()`, `source(slot: 0|1): InputSource` (contract `input.ts`: fills an `InputFrame` **once per sim tick** — sample devices *at tick time*, not only per rAF, so input latency ≤ 1 tick), a menu `nav()` frame (up/down/left/right/confirm/back/start with auto-repeat from any device),
device list + P1/P2 assignment, `rumble(slot, strong, weak, ms)`, change events (`onDevices`), remap API, settings (deadzone, calibration, label mode, per-device profile), and pure helpers.
- **Gamepad API**, primary target: **Nintendo Switch Pro Controller over Bluetooth**. Detect Nintendo devices by `id` string / vendor `057e` (Pro `2009`, Joy-Con L `2006`, Joy-Con R `2007`, charging grip `200e`; parse Chrome-style `Vendor: 057e Product: 2009` and Firefox-style `057e-2009-…` ids).
  **Verify indices at implementation time**: you can't pair hardware here, so encode the *known* tables and make every uncertainty overridable by the user through the Controller Check remap ("press the button you want for Strike"). Known facts to start from: with `mapping === 'standard'` (Chrome/Edge on Win/macOS/Linux, Safari/macOS): buttons 0 bottom (Nintendo **B**), 1 right (**A**), 2 left (**Y**), 3 top (**X**), 4 L, 5 R, 6 ZL, 7 ZR, 8 Minus, 9 Plus, 10 L3, 11 R3, 12–15 D-pad U/D/L/R, 16 Home, 17 Capture; axes 0/1 left stick, 2/3 right stick.
  With `mapping !== 'standard'` (Firefox on Windows/Linux/mac, older Chrome builds) use **explicit tables** keyed by (vendor, product, browser family): typical DirectInput-style layout is buttons 0=B, 1=A, 2=Y, 3=X, 4=L, 5=R, 6=ZL, 7=ZR, 8=Minus, 9=Plus, 10=L3, 11=R3, 12=Home, 13=Capture, with the **D-pad exposed as a hat axis** (axis 9 in Chrome-legacy, values ≈ −1, −0.714, −0.428, −0.143, 0.143, 0.429, 0.714, 1, neutral ≈ 1.286/3.286) — decode it. Triggers may appear as analog `value`s or as axes at rest −1.
  Document exactly what you did/didn't verify (in README "Browser support notes" and `DECISIONS`-style proposal); do not claim hardware verification you don't have. Test your tables against **fake `Gamepad` objects** in unit tests (and with Playwright by injecting a fake `navigator.getGamepads`).
- Also: **single sideways Joy-Cons** (one per player; rotate stick axes 90°, SL/SR as shoulders, data-driven profile), **combined Joy-Cons** if the browser exposes them as one device, Xbox (standard), PlayStation DualShock4/DualSense (standard + non-standard fallbacks), generic standard pads, and **two keyboard layouts** for local 2P (P1: WASD + J/K/L/U/I…, P2: arrows + numpad/`;'` cluster — your call, put them in the README, avoid ghosting-prone combos; `event.code`-based so AZERTY works).
- **Default layout** (Nintendo positions): **Y Strike · X Crush · B Surge · A Signature · ZR Ultimate · ZL Guard · L/R feint-cancel · + pause · − training overlay**; left stick / D-pad moves + aims. Xbox/PS pads map by *position* to the same layout. Remapping persisted in `localStorage` (try/catch — it may throw/return empty; the game must work without).
- **Nintendo labels:** when a Nintendo controller is detected show Nintendo labels/positions (A right, B bottom, X top, Y left) in prompts; an option chooses **positional vs label-based confirm** (positional: bottom button confirms on every pad; label-based: Nintendo A confirms on Nintendo pads, Xbox A on Xbox, etc.).
- **Radial deadzone** with rescale (default ≈ 0.15–0.2, adjustable), **stick calibration** (centre offset + max range capture, persisted per device), hot-plug (`gamepadconnected/disconnected`, and re-scan since browsers only expose pads after the first input), **"press any button"** activation flow, **P1/P2 assignment** (auto: first activated pad → P1; assignment screen lets players swap/choose keyboard/pad).
- **Rumble** via `gamepad.vibrationActuator?.playEffect('dual-rumble', …)` (and `hapticActuators` fallback) — `rumble()` is rate-limited and never throws. **Optional WebHID enhancement** (`src/input/webhid.ts`) behind an explicit user button in Chrome (`navigator.hid.requestDevice({filters:[{vendorId:0x057e}]})`): enable the Pro Controller's full 0x30 input reports and read buttons/sticks with lower latency and richer rumble; feed it into the same manager as another device; **degrade silently** if unavailable/denied/errors (feature-detect; never a console error).
- Pure modules (`profiles.ts`, `mapping.ts`, `deadzone.ts`, `nav.ts`, `remap.ts`…) with thorough unit tests: every standard/non-standard table, hat decoding, deadzone maths (radial, rescale, ≤ 1 magnitude), edge detection (`pressed/released` are per-tick edges), remap persistence round-trip, label modes, sideways Joy-Con rotation, hot-plug reassignment.

## 2. UI (`src/ui`)
Export `createUI(deps): GameUI` (contract `ui.ts`; you define `UIDeps` in `src/ui/types.ts`: input manager, titan info list `{id,name,nameKo,accent,tagline,attributes}`, a `PortraitProvider (id) ⇒ {pixels,w,h}` (the app wires B3's generator; in `dev/ui` use synthetic sprites), stage list, `implementedTitans/Stages`, storage). **All UI is rasterised in-pixel** into ONE screen-space `RenderLayer` at 640×360 (transparent where the scenery should show through) —
never DOM. Build a small **`PixelCanvas`** toolkit (`src/ui/pixel/`): rect/9-slice panels with dithered edges, sprite/icon blit with palette, pixel-perfect text with a **bitmap font** (crisp 5×7-ish Latin numerals/caps + lowercase, plus **Hangeul**: compose syllables from jamo (initial/medial/final layouts) at ~9–11 px so titles/names like 아득, 마지막 하나, 넥서스, 블랙홀, 초신성, 행성, 소행성 render correctly; unit-test composition),
dithered gradients, ramps, animated tickers. Style: **Korean-minimalist restraint** — generous negative space, hairline frames, one accent colour per titan (`ui.accent`), quiet motion; never cluttered. Hue-shifted palette; nothing that looks like a default rectangle.
Screens (state machine, keyboard/pad navigable, sound on every action):
`title` (pixel-art logotype **ADEUK: TITANS** + 아득; live scenery shows through; menu: Versus · vs AI · Training · Controller Check · Options; idle timer → `idleSeconds` for the 60 s AI-vs-AI attract) → `mode` → `assign` (P1/P2 device assignment, "press any button") → `select` (six titans as **live portraits** with attributes as pixel bars, tagline, destruction signature + failure mode text; unimplemented titans shown greyed with "coming soon" **only until Phase 2** — drive off `implementedTitans`) → `stage` (five stages with palette swatches; unimplemented greyed) →
`controller` (**Controller Check**: a drawn pixel controller (Pro layout) lighting every button live, analog trigger fill, both stick positions with deadzone ring, raw axis/button index readouts, device id/mapping/vendor info, remap mode, calibration wizard, rumble test, WebHID button) · `options` (volumes, deadzone, label mode, confirm mode, quality, keybinds) · `hud` · `pause` · `results` · `attract` overlay.
**HUD** (draws from `HudState`/`FighterView`s): for each titan a **live pixel portrait of its remaining body** (area-sampled from `view.body.map.pixels` into ~56 px, refreshed every few ticks, so the damage is visible in the HUD), **integrity %** (`view.integrityPct`), resource pips/bar (`view.resource/resourceMax`, `def.resource.display`), ultimate meter, guard health when Guard is up, round-win pips (best of 3), round timer, name plates (Latin + Hangeul), and an **announcer** line (ROUND 2 · FIGHT · K.O. · 승리!). Minimal, elegant, never covers the fight (top edge + slim bottom strip).
**Training mode overlay**: frame data table for the current move of each fighter (startup / active / recovery, phase, frame counter, hit/block advantage if derivable from the last exchange), toggles for hitbox overlay and matter debug overlays (`temperature/integrity/bonds/infection/islands/stress`), dummy settings (idle/guard/AI), reset positions/heal — emit `UIAction`s; the Lead wires them.
Everything unit-testable headless: render screens into a `Uint32Array` in Node, write PNGs with `tools/lead/png.ts`, **read them**, iterate. `tools/ui/sheet.ts` renders every screen (with fake deps/`FighterView`s at intact/50/10) to `.scratch/ui/*.png`.

## 3. Audio (`src/audio`)
Export `createAudioEngine(): AudioEngine` (contract `audio.ts`). **Procedural WebAudio only, no assets.** Graph: voices → per-bus (sfx/music) → **long convolution reverb** (generate the impulse response procedurally: dense, dark, long-tailed) → **master compressor + hard brick-wall limiter** (nothing ever clips) → destination.
`unlock()` creates/resumes the context on a user gesture; latency: `latencyHint:'interactive'`, schedule against `currentTime`, **hit → audible ≤ 50 ms**. Sub-bass impact synth with long tails for heavy blows; layered by `energy`/`heavy`/`onDamaged`.
**Per-titan sonic signatures** (both needed now, the rest Phase 2 — structure it so a titan voice is one file implementing a small interface): **Last One** — glassy celadon tones: inharmonic bell/glass partials, detuned sine shimmer, ceramic "tink", high fracture-crack bursts, a soft breathing pad when tendrils move, eye-flare swell on Gaze charge/release; **Asteroid** — rock crunch (filtered noise + granular gravel), whistling doppler for the tumble/surge, iron-ringing on ejecta, thuds.
React to `SimEvent`s: `move`, `charge`, `release`, `surge`, `hit` (by `type`: FRACTURE = glassy crack + shear, KINETIC = crunch + boom, plus `blocked` variants), `guard`, `shockwave`, `ko`, `matter` (detach/crack/consume…), `ultimate`, `round`, `cue`; plus `UiSoundEvent`s. Pan by world x relative to `AudioScene.listenerX`; slow pitch/tempo with `timeScale`.
**Adaptive score**: a generative drone bed (per-stage root/mode) + rhythm layers (sparse sub-bass pulses, low taiko-like hits, airy percussion) that fade in with `AudioScene.intensity`, calmer in menus, a tense drop on low integrity, a resolving swell on round end. No loops of samples — everything synthesised and evolving.
Testing: use `OfflineAudioContext` (in Node via a tiny shim? no — run in headless Chromium through Playwright, or structure DSP so the pure parts (envelopes, IR generation, note tables, scheduler logic) are unit-tested in Node and the graph is verified in the browser). Verify numerically: peak ≤ 1.0 after the limiter under a worst-case storm of events, non-silence, sensible spectral centroid per titan (glassy = high, rock = low-mid), reverb tail length, event → first audible sample latency.
`dev/ui/audio.html`: an audition page (buttons per event/titan/intensity) so the Lead and future you can trigger every sound.
